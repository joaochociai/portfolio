Plataforma de Cobrança

Plataforma financeira de recuperação de crédito com dashboards BigQuery em tempo real, régua de cobrança escalonada e configurável, controle de chargebacks multi-adquirente e automação de disparos via plataformas de mensageria e automação de marketing.

📊 Módulo 01 — Dashboard Executivo

Inteligência de Dados em Tempo Real

Dados do BigQuery materializados no Firestore via Cloud Functions diárias. O front-end lê documentos já agregados com ID DD-MM-YYYY, eliminando latência de query analítica no momento da apresentação.

  • Padrão CQRS: BigQuery executa queries pesadas 1×/dia → resultado materializado no Firestore → front-end com latência <100ms
  • Canal próprio e de integração: KPIs de disparos, débitos e pagamentos por etapa da régua, separados por fonte
  • Trend badges automáticos: variação percentual calculada entre períodos (↑ verde / → amarelo / ↓ vermelho)
  • Desempenho jurídico: acordos via e-mail, via mensageria, termos e taxa de conversão

🔄 Módulo 02 — Gestão de Chargeback

Controle Multi-Adquirente

Múltiplas adquirentes centralizadas em uma interface com semáforo visual de prazo. Dados importados do CRM via integração. Cada disputa perdida por deadline é receita revertida — o sistema elimina esse risco.

  • Semáforo de prazo: 🔴 <2 dias · 🟡 2–5 dias · 🟢 >5 dias — calculado por status automaticamente
  • KPIs em tempo real: win rate, valor em aberto, docs pendentes, casos em análise
  • Rastreamento por TID: ID único da transação na adquirente como chave de auditoria imutável
  • Agrupamento por e-mail: múltiplos contratos do mesmo cliente unificados na tela

📞 Módulo 03 — 3ª Cobrança e Régua

Régua de Recuperação Inteligente

Gerencia inadimplentes na janela crítica pré-jurídica. Régua de cobrança escalonada, com etapas calculadas dinamicamente. Agrupamento anti-cartesiano por documento. Trilha de auditoria arrayUnion() append-only — cada ação é imutável.

  • Régua escalonada: etapa atual de cada caso calculada dinamicamente em tempo real

Desafios Técnicos Superados

Os problemas mais complexos de ambos os sistemas — com as soluções de arquitetura que os resolvem

01 / BIGQUERY Cobrança

Produto Cartesiano no CRM

O Problema

Um aluno com 3 contratos no CRM aparecia com 3× o valor real de débito em JOINs ingênuos — tornando os números de inadimplência completamente imprecisos para a diretoria.

A Solução

Deduplicação em dois níveis: ROW_NUMBER no BigQuery antes de agregar, e agrupamento em memória no front-end antes de qualquer renderização de KPI.

ROW_NUMBER() OVER ( PARTITION BY cpf ORDER BY data_vencimento ) rn -- only rn = 1 enters the aggregation
02 / FIRESTORE Cobrança

Consistência Financeira Centavo a Centavo

O Problema

Firestore tem consistência eventual. Dois operadores atualizando o mesmo registro de dívida simultaneamente poderia resultar em dados corrompidos — inaceitável em contexto financeiro.

A Solução

writeBatch() para atomicidade multi-documento, arrayUnion() para trilha append-only, IDs determinísticos para idempotência em reimportações e serverTimestamp() em todos os campos de data.

const batch = writeBatch(db); // all or nothing — no partial state batch.update(ref, { HistoricoLogs: arrayUnion(log), updatedAt: serverTimestamp() // no client clock }); await batch.commit();
03 / ARQUITETURA Ambos

BigQuery Analítico sem Latência de Leitura

O Problema

Consultar BigQuery diretamente a cada acesso ao dashboard seria lento (2–5s por query) e caro. Inviável para uma diretoria que precisa de dados instantâneos.

A Solução

Padrão CQRS simplificado: Cloud Functions executam queries pesadas 1×/dia e materializam o resultado no Firestore. Front-end lê sempre documentos já prontos — latência <100ms.

// BigQuery (1x/day via Cloud Function) // ↓ materialize result // Firestore: reports/DD-MM-YYYY {} // ↓ front-end reads (< 100ms) await getDoc(doc(db,'reports',today))
04 / MENSAGERIA CX

Deduplicação de WhatsApp em Escala

O Problema

Com a Cloud Function disparando a cada 5 minutos, o mesmo aluno recém-matriculado poderia receber a mensagem de onboarding múltiplas vezes — deteriorando a experiência do cliente.

A Solução

Coleção Firestore dedicada como guard de idempotência. Antes de qualquer disparo, consulta uma coleção-guard pelo ID do destinatário. Se existir, pula. Se não existir, dispara e registra atomicamente.

// Idempotency guard const ref = doc(db, 'dispatched', id) const snap = await getDoc(ref) if (snap.exists()) continue // already sent await dispatch(recipient) // send await setDoc(ref, { dispatchedAt, templateId })
05 / DATA Cobrança

Régua com DST e Calendário de Feriados

O Problema

Calcular as etapas da régua em produção exige respeitar o horário de Brasília (DST), pular fins de semana e ignorar feriados cadastrados — garantindo que cada ação caia sempre em dia útil.

A Solução

Toda aritmética de datas forçada em America/Sao_Paulo via Intl. Feriados consultados por documento Firestore indexado por data ISO. Push automático para o próximo dia útil.

// Always America/Sao_Paulo dates let d = nextStage(base) // skip weekends and holidays while (isHoliday(d) || isWeekend(d)) d++
06 / ESTRUTURA CX

Modelo de Dados Flat para Escalas

O Problema

Escalas têm estrutura matricial (pessoa × dia × turno) que em Firestore resultaria em arrays aninhados — gerando custos de leitura por documento aninhado e dificultando atualizações pontuais.

A Solução

Modelo flat com chaves compostas: cell_YYYY-MM-DD_CARGO = nomes (slash-separated). Um único documento por mês por setor. Atualização pontual sem sobrescrever o documento inteiro via update() com campo específico.

// One doc per month/sector — composite key { "cell_2026-06-16_Atendente": "Ana/João", "cell_2026-06-16_Supervisora": "Maria", "label_week1_turno_horario": "9h–17h" }
